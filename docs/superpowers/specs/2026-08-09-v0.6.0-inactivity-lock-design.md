# Design Spec: Inactivity Lock (v0.6.0)

**Date:** 2026-08-09
**Branch:** `feature/v0.6.0-inactivity-lock`
**Status:** Approved

---

## Overview

**Inactivity Lock** panics (and optionally locks) after a configurable period of no user input. It fills the gap Proximity Lock cannot cover: users without a paired Bluetooth device, or without BLE hardware at all, currently have no automatic protection when they walk away from an unattended Mac.

This was the #1-ranked candidate in the v0.5.0 research report. Scope for v0.6.0 is this one feature only — WiFi geofencing (also proposed in that report) was explicitly deferred.

---

## Feature: Inactivity Lock

### What it does

When the Mac has received no keyboard/mouse input for a configurable timeout, the app fires Panic Mode and, depending on settings, locks the screen. A short countdown warning appears before firing so the user has a chance to cancel by simply touching the keyboard or mouse. The feature backs off automatically when a display-sleep-preventing assertion is held (e.g. video playing, presentation running) since that indicates the user is present but not typing.

### Components — new folder `VigilScreen/Features/InactivityLock/`

**1. `IdleTrigger`** — pure struct, Foundation only, no timers or system calls. Holds `phase` (`waiting` / `warning` / `fired`) and a single `evaluate` method:

```swift
struct IdleTrigger {
    enum Phase { case waiting, warning, fired }
    enum Action {
        case showWarning(secondsRemaining: TimeInterval)
        case cancelWarning
        case fire
    }

    var phase: Phase = .waiting

    mutating func evaluate(
        idleSeconds: TimeInterval,
        displaySleepPrevented: Bool,
        panicAlreadyActive: Bool,
        timeout: TimeInterval,
        warningLead: TimeInterval
    ) -> Action?
}
```

Mirrors the `ShoulderSurfingTrigger` pure-struct pattern used elsewhere in the codebase: all inputs are parameters, no singleton reads, fully unit-testable in isolation. `IdleTrigger` decides *when* to fire; `InactivityLockManager` decides *what firing does* (panic only vs panic-and-lock) by reading `inactivityLockAction` at fire time.

**2. `InactivityLockManager`** — `@MainActor` `ObservableObject` singleton. Owns the timer and performs the two system reads:
- `CGEventSourceSecondsSinceLastEventType` for idle seconds
- `IOPMCopyAssertionsStatus` for whether a display-sleep-preventing assertion is currently held

Feeds both into `IdleTrigger.evaluate` and performs the returned action. Publishes `isCountingDown` / `secondsRemaining` for the menu bar and popover countdown surface.

Arms a single timer for the interval until the next decision point (not a 1s repeating tick), dropping to per-second ticks only while a warning is on screen — consistent with `ScreenShareDetector`'s zero-CPU-at-idle approach.

**3. `IdleWarningPanel`** — non-activating floating `NSPanel` (`.nonactivatingPanel`, `.floating`) hosting a small SwiftUI countdown view, shown on the screen containing the pointer. Non-activating is required: the app runs with `.accessory` activation policy, and a focus-stealing panel would itself count as user interaction, defeating its own purpose.

**4. `InactivityLockView`** — Settings pane matching the existing feature panes (Proximity Lock, Shoulder Surfing, Presentation Mode).

### State machine (`IdleTrigger`)

- `waiting → warning` when `idleSeconds >= timeout − warningLead`, AND no display-sleep assertion held, AND panic not already active, AND `warningLead > 0`.
- `waiting → fired` directly when `warningLead == 0` and `idleSeconds >= timeout` (same guards).
- `warning → waiting` (`cancelWarning`) when idle drops (any input), an assertion appears, panic becomes active from another source, or the feature is disabled.
- `warning → fired` at `idleSeconds >= timeout`.
- `fired → waiting` only once `idleSeconds` drops below `timeout` again — this is what prevents re-firing every tick while still idle.

On fire: record `.inactivity` in `LockHistoryStore`, call `PanicModeManager.triggerPanic()`, and call `LockEngine.lockScreen()` only if the action setting is `panicAndLock`.

### Edge cases

- **Panic already active** (hotkey / proximity / shoulder surfing / presentation) → fully suppressed; no second panic, no duplicate history entry.
- **Assertion appearing mid-warning** cancels the warning outright (no stale panel left on screen).
- **`warningLead >= timeout`** is clamped so the warning cannot start before the clock does.
- **Settings changed mid-countdown** re-evaluate immediately rather than waiting out the old timer.
- **Session already locked** → suppressed. Detected via `CGSessionCopyCurrentDictionary` / `kCGSessionOnConsoleKey`, read by the manager and folded into the same `panicAlreadyActive` suppression input passed to `IdleTrigger` — keeping the pure trigger free of system calls and avoiding a second suppression input.
- **System sleep/wake:** idle resets naturally on wake; timer re-armed.
- **Multiple displays:** the warning panel appears on the screen containing the pointer.

### Error handling

If the `IOPMCopyAssertionsStatus` query fails or returns an unexpected shape, treat it as "no assertion held" and let the timer proceed — the security-forward default, with the warning overlay as the escape hatch. Log once, not on every tick — no silent swallow, no per-tick log spam.

### Settings (4 new, all cloud-synced)

None of these settings depend on per-machine hardware, so they follow `proximityLockEnabled`'s sync behavior, not the camera/Touch ID controls that stay per-machine.

| Key | Type | Default | Range |
|---|---|---|---|
| `inactivityLockEnabled` | Bool | `false` | — |
| `inactivityLockTimeout` | Double (minutes) | `5` | 1–60 |
| `inactivityWarningLead` | Double (seconds) | `10` | 0–30 (0 = no warning) |
| `inactivityLockAction` | String enum: `panicOnly` \| `panicAndLock` | `panicAndLock` | — |

Each of the four settings needs:
- `Keys` entry
- `persist(...)` call
- `allCloudKeys` membership
- an `applyCloudUpdate` branch
- addition to `CloudSyncStore.settingsKeys` — that set is what actually decides fan-out when another Mac changes them, and is easy to miss

### Surfaces

- New Settings pane: enable toggle, timeout, action picker, warning lead.
- Countdown reuses the existing menu bar + popover countdown surface that Proximity Lock uses.
- New `LockTriggerType.inactivity` case with its own icon and label in `LockHistoryView`, plus a label in `AuditSummaryGenerator.triggerLabel`, plus addition to the trigger array in `testBuildPrompt_allTriggerTypes_haveLabels` so a missing label fails the test rather than silently emitting "unknown" into a summary.

## Testing

### `IdleTriggerTests.swift` (new)

Pure, `XCTestCase`, `@MainActor` per project convention (the project builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`):

- Nothing before threshold
- Warning at `timeout − lead`
- Suppressed when assertion held
- Suppressed when panic already active
- Cancel when idle drops mid-warning
- Fire at timeout
- Straight-to-fire when lead is 0
- Lead clamping (`warningLead >= timeout`)
- No re-fire while still idle after firing
- `fired → waiting` after idle drops

### `SettingsStoreTests.swift` (additions)

- Round-trip and clamping for `inactivityLockTimeout`, `inactivityWarningLead`
- `inactivityLockAction` enum persistence
- `inactivityLockEnabled` default and toggle

### Two hard isolation constraints

Both learned from real flakes in this project — stated here so they aren't reintroduced:

- `IdleTrigger` tests take config as parameters and must **never** touch `SettingsStore.shared`.
- The four new settings keys are mutated by `SettingsStoreTests` alone. No second test class may write them, or they flake under parallel XCTest execution.

### Not unit-testable (manual verification required)

- The idle-time and assertion system reads (`CGEventSourceSecondsSinceLastEventType`, `IOPMCopyAssertionsStatus`)
- Warning panel presentation and focus-stealing behavior
- `LockEngine.lockScreen()`
- Timer scheduling across sleep/wake

## What is NOT in v0.6.0

- WiFi geofencing (explicitly deferred; was the #5-ranked candidate in the v0.5.0 research report)
- Any change to Proximity Lock, Shoulder Surfing, or Presentation Mode triggers
- Per-machine (non-synced) variant of these settings
